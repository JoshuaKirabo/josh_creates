At Tellistic Technology Services, SurveyCTO collected field submissions and organized the answers into a CSV with consistent columns. I used AzCopy to upload that file to Azure Data Lake Storage Gen2. Azure Data Factory coordinated the Python transformations in Databricks and loaded the results into Azure SQL for the client’s reports.

01 / The situation

Before and afterBefore and after

Before

One source record could have several related entries

SurveyCTO forms captured text, numbers, and repeated answers. One submission could include several entries in a household roster, so counting rows in the processed data could overstate the number of source records. Analysts needed a way to distinguish each record from its related entries.

After

Survey responses become queryable tables

I used Python in Azure Databricks to flatten the repeated answers, cast dates and numbers, and handle missing values. Azure Data Factory coordinated the work and loaded the results into Azure SQL, giving the client a consistent starting point for analysis.

03 / The delivery

Inside the buildInside the build

01

From field submissions to a CSV for Azure

AzCopy CLI

SurveyCTO used the form definition to give each answer a named field and each submission a key. That kept repeated answers linked to their original submission when the data was exported to CSV. I uploaded the local export with azcopy copy to the raw landing folder in Azure Data Lake Storage Gen2. Creating or overwriting /container9/folder9/data.csv raised a Blob Created event. The storage event trigger started the Azure Data Factory pipeline. The notebook activity used a linked service, a saved connection that tells Data Factory which Databricks workspace and compute to use. Data Factory authenticated its request with a Databricks personal access token (PAT), then started the cleaning notebook.

Inside Databricks, dbutils.secrets.get(scope, key) retrieved the service principal’s client secret directly from Azure Key Vault through a Key Vault-backed secret scope. The notebook used that credential to authenticate the storage mount over abfss://, read the raw CSV and write the cleaned file to the same container.

02

Flattening nested repeat groups

Databricks · Python

A repeat group contains multiple entries linked to one source record. For example, a household record with three members contributes one household row and three related member rows. I flattened the nested groups in Python. Keeping the submission key with each entry lets an analyst join the records and still count households or members at the correct level.

  • Azure Databricks
  • Python
03

Types and nulls before load

Explicit casts

I cast numeric and date fields explicitly before loading them into SQL and handled null values in the notebook. A blank count and a reported count of zero carry different information. Keeping missing values distinct from zero preserves that difference in SQL.

04

Chasing duplicate records

Debugging

I investigated duplicate records during development. Repeated submission keys can be legitimate in a table of repeated answers. A useful check is to count distinct submissions in the parent data, then check repeat entries separately using their parent key and entry identifier. Replaying the same batch should leave both totals unchanged.

05

Wildcard paths for Spark’s output

Data Factory

Spark generates part filenames when it writes a dataset. A copy activity tied to one generated filename can miss the next run’s output. The notebook read the incoming CSV and used coalesce(1) to write one part file in the processed output folder. Both folders belonged to the same container in one ADLS Gen2 account. I configured a wildcard path in Data Factory to pick up the resulting part file. Scoping the match to the current batch also keeps earlier files out of a replay.

  • Spark
  • Azure Data Factory
06

Loading Azure SQL

Azure SQL

When the notebook succeeded, Data Factory started the Copy Data activity. Azure Integration Runtime read the part file from the processed output folder. The Azure SQL sink cleared the target table with a pre-copy script immediately before inserting the new rows. In ADF Studio, Monitor → Pipeline runs shows the run’s status, start time, and duration. Opening the run shows whether notebook11 and Copy Data succeeded and any activity error details. The refreshed SQL table gave the client a relational source for queries and reports. For example, a report could group distinct submission keys by date, while a separate query could count entries within a repeat group.

  • Azure SQL

04 / The outcome

What changedWhat changed

New batches follow the same processing steps

The notebook applies the same field rules to each batch, and the wildcard copy path accommodates new Spark filenames. Analysts can start with the SQL tables each time another batch is loaded.

Refresh timing follows the reporting need

When a new CSV arrives in raw storage, Data Factory starts the transformation and SQL load. The operating design calls for a failed step to identify the affected batch and stop publication until it can be rerun.

Measuring the time saved

Compare a manual batch and an automated batch of similar size. Record hands-on preparation minutes and elapsed time from CSV intake to queryable tables. Check the distinct submission count and repeat-row count alongside those timings so any speed gain is measured against a complete load.
